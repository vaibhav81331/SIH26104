1. Which stage is the AI model

M5 — Forecast is the only trained machine-learning model in the system. But the reason why it sits there, and not in M4, is the most important design decision in this project, so it's worth being precise:

Stage	Nature	Learned from data?
M1 Ingest	Deterministic parsing + calibration	No
M2 Indices	Physics — heat-balance equations	No
M3 Places	Joins, interpolation, index construction	No
M4 Risk	Statistics — quasi-Poisson GLM baseline + transferred risk curve	Partly (baseline only)
M5 Forecast	Machine learning — LightGBM	Yes ← the AI
M8 Explainability	SHAP over M5	Reads M5

What the AI actually predicts — and why it isn't deaths.

The instinctive design is "train a model to predict heat mortality." That is impossible with this data, and this is the finding from earlier: your mortality file covers 2007–2011, the weather covers 2015–2025. Zero overlapping days. There is no (weather, deaths) pair anywhere in the dataset to learn from. Any team that claims to have trained a mortality model on these two files has either not checked the dates or has leaked something.

So the pipeline splits into a learned half and a transparent half:

ML (trained on nasapower_odisha)          Epidemiology (no training)
──────────────────────────────────        ──────────────────────────────
history ──► HTSI forecast D+1…D+5  ────►  baseline × RR × vulnerability
            + uncertainty bands            ──► expected excess deaths

The ML model forecasts thermal stress, which is exactly what your mandated dataset supports — 46.2 million labelled hourly observations across 480 cells and 11 years. That's a genuine, well-posed supervised problem with real labels and real skill scores.

The conversion from thermal stress to mortality risk is then a deterministic epidemiological transform, every term of which is inspectable — not a black box with "AI" written on it. That separation is defensible to a health department in a way that a single opaque model would not be.

Model spec (M5): LightGBM, one model per horizon D+1…D+5 (direct, not recursive, so errors don't compound), quantile objective τ = 0.1/0.5/0.9 plus split-conformal calibration for honest intervals, temporal split (train 2015–2022, validate 2023, test 2024–25), benchmarked against persistence and climatology baselines. On the live path it also acts as a statistical downscaling layer on top of NWP forecasts, learning the ward-level structure a 27 km grid can't resolve.

2. How to run what exists

The package is already installed editable, so imports work from anywhere. Fresh setup on another machine:

pip install -e ".[dev]"

Run the validation suite — this is the fastest proof the science layer is correct (37 tests, ~40 s):

python -m pytest tests/ -q

Rebuild the hourly panel from the 5,279 CSVs (~11 min, already done — skips completed years unless forced):

python -c "from ushma.ingest.nasapower import ingest; ingest()"

Compute thermal indices and daily aggregates (~50 min for all 11 years — currently running):

python -c "from ushma.indices.pipeline import build_daily; build_daily()"

Try the index engine directly on any conditions:

python -c "from ushma.indices.wbgt import wbgt_liljegren; print(wbgt_liljegren(t_c=42., dewpoint_c=28., wind_ms=1.5, pressure_kpa=100., solar_wm2=950., cos_zenith=0.92, direct_fraction=0.8))"

What you get: data/interim/hourly_grid/ (351 MB Parquet, 46.2 M rows), data/interim/utc_offsets.json (the measured per-cell time calibration), reports/ingest_qc.csv, and data/processed/daily_cell.parquet once the build lands.

There is no dashboard or API to run yet — those are M6. Right now the runnable surface is the pipeline and the test suite.
